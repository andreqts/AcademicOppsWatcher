## What Worked

- **File-based Q&A loop** for the grilling interview (writing rounds of questions into a scratch `QUESTIONS.md`, user answering inline, agent reading back) worked well across 3 rounds and was explicitly requested by the user over a pure chat back-and-forth.
- **Verifying every unfamiliar API against primary sources before writing it into the spec/design** caught real problems the user's own working assumptions didn't have: `openrouter/auto` cannot be restricted to free-only (must use `openrouter/free` instead); Jev's exact request/response schema had to be pulled from OpenRouter's own docs, not guessed; public-repo Actions logs are confirmed publicly visible, which forced the `AD-001` no-raw-PII-in-logs rule.
- **User actively pressure-tests the design by reading the Mermaid diagram literally** — this surfaced two real logic gaps (a Jev failure silently rescued by the free-tier fallback produced zero alert; a stale `P1-AC17` cross-reference pointing at the wrong AC after a renumbering). Take diagram-literalism from this user seriously; it has a good hit rate for finding real bugs, not just cosmetic complaints.
- **Renaming every Mermaid node id to match its function name** (no more `R`, `S`, `E`, `V1`...) resolved a recurring pattern of "wait, what does this node connect to" questions. Default to descriptive ids from the start next time, don't wait for complaints.
- Running `validate_spec.py` after every edit (not just at milestones) kept the spec provably clean throughout heavy iterative editing — cheap and worth doing on every touch.

## What Didn't Work / Watch Out For

- Web search results for "Jev AI" initially returned a cluster of suspicious-looking marketing/SEO content (jevai.org, jev-ai.net, hyperbolic "193x faster" claims) mixed in with legitimate OpenRouter documentation. **Only trust `openrouter.ai`-domain results for Jev/OpenRouter facts** — the satellite sites were never used as sources, and that distinction should stay explicit in any future edit to this area.
- Two separate `WebFetch` calls to OpenRouter's own docs returned **inconsistent endpoint paths** for the Jev Decisions API (`/api/alpha/decisions` vs. a malformed `/api/v1/api/alpha/decisions`). This was never resolved with certainty — the design isolates the exact endpoint behind one function (`validate.py::_call_jev`) specifically so this uncertainty doesn't propagate; **the Tasks/Execute phase must re-verify the live endpoint before writing that function**, not trust either of the two conflicting research findings.
- AC renumbering is dangerous in this file: an earlier insertion shifted P1's ACs by one, and a cross-reference elsewhere in the spec (`P1-AC17` in the P3 story) was missed and pointed at the wrong requirement for at least one full turn before being caught on a manual re-read. **When inserting a new AC, grep the whole file for `P1-AC` / `P2-AC` cross-references before finishing the edit**, or append new ACs at the end of a story's list instead of inserting mid-list.

## Decisions made this session (all recorded in spec.md / design.md)

- **Jev question (P1-AC20), verbatim in Portuguese:** "Esta é uma oportunidade de concurso com vagas para professor efetivo ou temporário (PSS ou Substituto), nas áreas de Computação (Engenharia da Computação ou Ciência da Computação ou afins), Engenharia Elétrica, Engenharia de Energia, para atuação da cidade de Foz do Iguaçu/PR?"
- **Email addressing:** all emails use Bcc; To: is the project's own sending address (`GMAIL_ADDRESS`).
- **False positives** are stored in `seen.json` with `verdict: false_positive` and never re-classified, reported or emailed. Only ids not already in `seen.json` go to Jev.
- **Dedup key:** SHA-256 of the normalized URL (confirmed).
- **Notification retry:** a `notified` flag is set only after a successful send. Each run emails every genuine, open, not-yet-notified item (P1-AC9, P1-AC23). `seen.json` is saved *after* the send. With an empty recipient list, items stay pending and are sent once the list is filled.
- **Stale rule:** a run with any failed search query doesn't count toward the 3-miss rule (P1-AC21). A reappearing item returns without a re-notification if it was already notified (P1-AC22).
- **Queries:** 8 queries for UNILA, IFPR and **UNIOESTE** (`unioeste.br`, confirmed on the official site; it has a Foz campus). Each covers temporary and permanent (efetivo) roles. **UTFPR and UFPR were removed**: neither appears to have a Foz do Iguaçu campus.
- **Jev model:** `typesafe/jev-latest`, overridable through an optional `JEV_MODEL` environment variable / GitHub repo variable.
- **Stack:** pytest with all I/O faked (no network in tests), ruff for lint and format, code in `src/opportunity_watch/`, managed with `uv` (installed locally; Python 3.12.3; pytest and ruff are not installed globally, so use `uv run`).
- **Interfaces changed by the review:** `classify` returns `tuple[ValidationResult, list[FailureRecord]]`. `apply_run(found_ids, new_candidates, today, count_misses)` never overwrites a stored verdict or `notified` flag. New `NotifyResult(sent_to, skipped, failure)` model; a send error is returned, not raised. The entry point uses `raise SystemExit(main())`.
- Spec stories renamed **P2a** (config) and **P2b** (failure alerts); the traceability table maps every OPW id to its ACs (36 ACs).
